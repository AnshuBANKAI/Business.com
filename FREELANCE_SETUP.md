# Freelance site — setup & operations

The project is now four things in one repo:

| Area | URL | Who |
|---|---|---|
| Public site (services, case studies, enquiry form) | `/`, `/work/:slug` | anyone |
| **About me** (photo, bio, skills, experience, education, certifications, resume) | `/about` | anyone |
| Cinematic portfolio, opens with **"Who's here today?"**: About Anshu · Startup Founder · Client · Admin | `/series` | anyone (Client and Admin doors ask for sign-in) |
| Admin panel (CMS, leads, clients, client projects) | `/admin` | you only |
| Client portal (milestones, files, messages) | `/portal` | each client, their own projects only |

Client and Admin entry points are on every public page (header + the "Private areas" band above the footer) and in the `/series` picker.
If the API is down, the public site still shows its built-in content (from `shared/site-content.json`) instead of an error.

Stack: React + Vite (front end) · Express + MongoDB/Mongoose (API in `backend/`).

## 1. First run (local)

```bash
npm install && npm run setup       # root tools, then frontend/ and backend/ dependencies
cp backend/.env.example backend/.env # then edit backend/.env
npm run seed                       # creates your admin + starter content
npm run dev                        # web on :5173, API on :4000
```

`backend/.env` needs at least `MONGODB_URI`, `JWT_SECRET` (32+ random characters) and, for the seed,
`ADMIN_EMAIL` + `ADMIN_PASSWORD` (12+ characters). Use a free MongoDB Atlas cluster or a local `mongod`.
Sign in at http://localhost:5173/login. After the first seed you can delete `ADMIN_PASSWORD` from `.env`.

## 1b. Business features at a glance

- **Proposals** (Admin > Proposals): write the scope and price, send it, and the client accepts it online. The acceptance record (name, email, time, IP, SHA-256 of the exact text) is stored. Sent proposals are read-only.
- **Invoices** (Admin > Invoices): export-under-LUT, domestic CGST+SGST, domestic IGST, or no-GST. Numbers are assigned on send, per financial year, and never reused. Sent invoices are frozen; void and reissue instead. Clients view and print/save as PDF from the portal.
- **Business settings** (Admin > Site settings): legal name, address, GSTIN, PAN, LUT, SAC, bank details (private), WhatsApp, booking link, reply time, privacy contact, and the promises shown under the headline.
- **Legal pages**: `/privacy` and `/terms` are drafts written for this business. **Have a lawyer review them before launch.**
- **SEO**: sitemap, robots, per-page meta + structured data are generated by the server (production build only).
- **Two-factor sign-in** (Account page, for admin and clients): authenticator-app codes plus one-time recovery codes. Replay-proof, lock-out after 5 wrong codes, secrets encrypted at rest.
- **About page editor** (Admin > About page): skills, experience, education and certifications, with no code changes needed.
- **Insights blog** (Admin > Insights): write articles with simple formatting; they appear at `/insights`, in the sitemap and in an RSS feed (`/rss.xml`). Raw HTML is never rendered.
- **Automatic reminders**: invoices due/overdue, milestones awaiting approval, and a daily summary to you. See the card on Admin > Overview ("Run now").
- **Health checks**: `/api/health` (process up) and `/api/ready` (503 if the database is down); a secured `POST /api/cron/daily` for schedulers.
- **Launch checklist**: shown on the admin Overview and ticks itself off as you fill in settings.
- **Backups**: `npm run backup` (needs `mongodump`). Copy backups off the server. See `backend/scripts/backup.sh`.

See **BUSINESS_GAP_ANALYSIS.md** for the research behind these choices and what is still open.

## 2. Everyday use

1. **Admin > Site settings / Services / Case studies**: edit what the public site shows. The seeded text is a starting point; review it.
2. **Leads** arrive from the enquiry form. Move them new > contacted > proposal > won/lost and keep private notes.
3. **Clients > Create & get invite link**: send the link (it is also emailed if SMTP is set). The client chooses their own password.
   "New invite link" doubles as a password reset and signs them out everywhere.
4. **Client projects**: create a project for a client and add milestones. Set a milestone to **Delivered** to ask for approval;
   the client approves or requests changes from `/portal`. Files and messages live on the same page.

## 3. Deploying (one server, one domain)

```bash
npm run build                          # builds the React app into dist/
NODE_ENV=production npm --prefix backend start
```

In production Express serves `dist/` and the API from the same origin: no CORS, and cookies stay first-party.
Set these on your host (Render, Railway, Fly, a VPS...):

`NODE_ENV=production`, `MONGODB_URI`, `JWT_SECRET`, `PUBLIC_URL` and `CLIENT_ORIGIN` (both your https site URL),
`TRUST_PROXY=1` (behind a proxy/PaaS), plus optional SMTP settings. Serve over HTTPS: the session cookie is `Secure` in production
(to try the production build locally over plain http, run with `NODE_ENV=development`).

**Uploads need persistent storage.** Files go to `UPLOAD_DIR` (default `backend/uploads`). On hosts with an ephemeral disk
(Render free, Heroku) they disappear on redeploy: attach a persistent disk/volume or move uploads to S3/Cloudinary.

## 4. Security design (already in place)

- Passwords hashed with bcrypt (cost 12). Sessions are JWTs in `HttpOnly`, `SameSite=Lax`, `Secure` cookies (7 days).
- Roles are enforced **on the server** for every `/api/admin` and `/api/portal` route; the React route guards are only UX.
- A client's project lookup always includes their own id, so another client's data looks like "not found".
- Deactivating a client or re-inviting them bumps a token version, which ends their existing sessions immediately.
- Rate limits on login, invites and the enquiry form; honeypot field against bots; origin check on state-changing requests.
- Zod validation on every request body (also blocks NoSQL operator injection); only http(s) links are stored.
- Uploads: allow-listed types, 10 MB cap, random on-disk names, no SVG; client files are served only through authenticated routes as attachments.
- Strict Content-Security-Policy (no inline scripts), HSTS and other headers via Helmet.
